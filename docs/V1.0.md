# go-exec V1.0 (Authorized Ops) - Product/Engineering Recommendations

This document records a suggested "V1.0 final shape" for this fork of go-exec, assuming:

- Use case: authorized remote operations / authorized security exercises only.
- Integration: must support both CLI usage and Go library embedding (e.g. `vm_ops` orchestration).

Non-goals:

- Do not add features primarily aimed at unauthorized access, stealth, or lateral movement.
- Do not expand protocol/method surface area as a primary objective. Focus on reliability, auditability, and safe operation.

## V1.0 North Star

Make go-exec a "library-first + thin CLI wrapper" execution framework:

- `pkg/` exposes a stable, typed API and structured results.
- `cmd/` focuses on UX: flags/config parsing, output formatting, audit output.
- Every execution produces machine-readable, auditable results and consistent error classification.

## V1.0 Must-Have Deliverables (P0)

### 1. Stable Go API Contract (Embed-Friendly)

Add a small, stable contract under `pkg/goexec` for higher-level orchestration:

- `ExecutionRequest`
  - Target, auth, selected module/method, command/executable args
  - Timeouts (global, connect, output)
  - Output collection policy (off by default; explicit enable)
  - Cleanup policy (best-effort, strict, etc.)
- `ExecutionResult`
  - Target identifiers
  - Module/method
  - Timings and attempt metadata
  - Remote artifact paths (if any)
  - Output collection outcome (success/timeout/partial)
  - Cleanup outcome (success/failure + error)
- `ErrorKind` classification
  - Examples: `AuthError`, `NetworkError`, `RemoteCallError`, `InvalidInput`, `CleanupError`, `TimeoutError`
  - Must be stable for `vm_ops` retry/branching/reporting logic.

Implementation note:

- Keep method implementations in their module packages (`pkg/goexec/{wmi,dcom,scmr,tsch}`).
- Do not let CLI concerns leak into method implementations.

### 2. CLI Result Contract (Machine-Readable)

Separate "logs" from "results":

- Logging stays as-is (`--json`, `--log-file`, `--debug`, `--quiet`).
- Add a result output mode:
  - `--json-result` or `--result-file` to emit a single structured `ExecutionResult` (or JSONL for multi-run in future).
  - Ensure stable keys, no breaking changes without versioning.

### 3. Unified Timeout Model

Today, `--out-timeout` exists; V1.0 should standardize a full timeout surface:

- `--timeout` (overall execution timeout)
- `--connect-timeout` (TCP/session establishment timeout)
- `--out-timeout` (output collection timeout)
- `--out-poll-interval` (output polling interval)
  - `pkg/goexec/context.go` already has `ContextOptionOutputPollInterval`; expose it consistently in CLI.

### 4. Consistent Flag Validation (Reduce Footguns)

Make all "execute something" commands consistent:

- Enforce "exactly one of `--exec` or `--command`" where applicable.
- Ensure required flags are truly required.

Concrete examples to fix:

- `cmd/wmi.go`: `wmi proc` currently registers exec flags but does not enforce a "one required" rule.

### 5. Default Safety Guardrails (Authorized Ops)

Add guardrails that prevent accidental destructive behavior:

- `--dry-run` prints the effective request/result skeleton and exits without execution.
- For operations that modify remote state, require explicit confirmation:
  - Example: `--confirm` for service/task definition modifications.
- `--audit file` writes a tamper-evident (append-only preferred) JSON record of request + result.

### 6. Fix Deterministic Randomness

`internal/util/util.go` uses `math/rand` without seeding; across program launches the sequence is deterministic.

Requirements:

- Remove deterministic collisions for generated service names / task names / hostnames.
- Prefer `crypto/rand` or UUID-derived strings for uniqueness.

## V1.0 Engineering Baseline

### Tests

Focus tests on contracts and invariants:

- Flag validation for each subcommand (required, mutual exclusivity).
- `Request -> Result` shape stays stable (golden JSON tests are acceptable).
- Cleanup ordering and error aggregation (Cleaner is LIFO; ensure it stays that way).

### CI

Current CI runs `go test ./...` on Linux/Windows. Consider adding (optional):

- `go vet ./...`
- A small set of contract tests that run on all OSes without needing a live target.

## V1.1+ (Optional, High ROI)

### Output Collection Reliability

Improve output collection correctness without adding new execution channels:

- Avoid returning partial output when a remote file becomes readable before the remote process completes.
- Introduce a completion criterion (e.g. stability window, terminator marker, or metadata), but keep it optional.

### Config-First Operation

Add `--config` (YAML/JSON) support so `vm_ops` and CLI can share the same configuration schema:

- CLI merges: `config` + `env` + `flags` (flags override).
- Keep a `--print-effective-config` command for debugging.

### Supply Chain Hygiene

For internal distribution:

- SemVer releases and changelog discipline.
- SBOM generation and reproducible build notes (aligned with existing `.goreleaser.yaml`).

## Suggested Implementation Touchpoints

These are the likely places to implement V1.0 items:

- Stable contract types: `pkg/goexec/` (new files)
- Flag validation consistency: `cmd/*.go` (e.g. `cmd/wmi.go`)
- Timeout flags: `cmd/args.go`, `cmd/root.go`, `pkg/goexec/context.go`
- Audit/result output: `cmd/root.go` (PersistentPreRun/PersistentPostRun) and a small result emitter utility
- Randomness fix: `internal/util/util.go`
